# Translation guide

The dashboard ships complete Danish (`da`), English (`en`) and German (`de`)
catalogs in `index.html`; deployment settings live in external JSON configuration.
Every interface message is identified by a stable semantic key, such as
`tabs.dashboard` or `auth.notConnectedOn`.
The catalogs contain plain text, including named placeholders where a message
needs values from the application.

The translations need no build step, translation server or additional browser
dependency.
Chart.js is a separate local file used only for charts. The Docker image bundles
it at build time; manual installations download it as described in the README.

## Language selection

`SUPPORTED_LANGUAGES` defines each language's native label and formatting locale:

| Code | Native label | Locale |
| --- | --- | --- |
| `da` | Dansk | `da-DK` |
| `en` | English | `en-GB` |
| `de` | Deutsch | `de-DE` |

`resolveLanguage(saved, browserLanguages, configuredDefault = "auto")` selects
a supported saved preference first, then a configured `da`, `en` or `de` default,
then the first supported entry in the browser's ordered language list, and
finally English. The configured default comes from the external JSON file
described in the [configuration guide](CONFIGURATION.md); `auto` continues to
browser preferences. `normalizeLanguage(value)` accepts regional tags such as
`de-AT`, `en-GB` and `da-DK`, ignoring case and surrounding whitespace.
Unsupported saved values do not override a supported configured or browser preference.

The selected language is saved under `ph_combo_language` in `localStorage`.
If storage is unavailable, the page continues using its in-memory selection.
The selector uses native language labels so each language remains recognizable
regardless of the current interface language.

`setLanguage(language)` updates the document language, explicitly bound shell
text, navigation, server status and the active tab. The tab's unfinished form
values and focus are preserved through the re-render. Charts are recreated
with translated labels and the selected formatting locale. Route identifiers,
server configuration and authentication sessions are independent of language.

## Choosing keys and writing translations

Name keys after their meaning or interface role. Keep their names stable when
the wording changes. A translation must not use a Danish or English sentence
as its lookup key.

Add each new key to **every** catalog in `I18N`, and preserve the same set of
named placeholders in each language. Translate whole messages so each language
can choose its natural word order. For example, a new message could be defined
as follows inside the corresponding catalogs:

```js
// I18N.en
"example.updated": "Updated {domain} on {server}",

// I18N.da
"example.updated": "Opdaterede {domain} på {server}",

// I18N.de
"example.updated": "{domain} auf {server} aktualisiert",
```

Do not concatenate independently translated sentence fragments around a domain
or server name. Named values let translators move the values without changing
the application code.

All catalogs must be complete. The runtime falls back to English when a key is
missing from the selected language, then to the literal key if English is also
missing it. This makes a missing message visible while keeping the page usable;
the automated tests reject incomplete shipped catalogs.

## Rendering messages safely

Use the helper that matches the destination:

| Helper | Purpose |
| --- | --- |
| `msg(key, params = {})` | Plain text for `textContent`, attributes, confirmations, prompts, toast messages and chart labels |
| `htmlMsg(key, params = {})` | Escaped text inside a template that is assigned to `innerHTML` |
| `msgCount(baseKey, count, params = {})` | A plural message with a locale-formatted `{count}` |
| `fmtNum(value)` | A number formatted for the selected language |
| `fmtPct(value)` | A percentage; the input is already a percentage, so `12.5` means 12.5% |
| `fmtDate(value)` | A Unix timestamp in seconds, formatted as local date and time; missing timestamps display the translated “never” message |
| `localeCode()` | The selected formatting locale for sorting and other locale-aware APIs |

For plain text:

```js
status.textContent = msg("auth.notConnectedOn", { server: server.label });
```

For a message inside an HTML template:

```js
container.innerHTML = `<p>${htmlMsg("auth.notConnectedOn", {
  server: server.label
})}</p>`;
```

Pass the original parameter values to these helpers. `msg` interpolates once:
braces, dollar signs, Danish words and other content inside supplied values are
preserved literally. `htmlMsg` escapes the complete result, including the
parameters. Passing pre-escaped values to `htmlMsg` would escape them twice.

Keep markup outside the catalogs. Use `escapeHtml` for raw user or API values
inserted into HTML without a translated surrounding message. Domains, server
names, client names, comments, API error details and streamed Gravity output
are data; changing the interface language must not translate or rewrite them.

## Explicit bindings in static HTML

`applyI18n(root = document)` updates only elements with explicit translation
attributes. It does not inspect or replace arbitrary DOM text.

| Binding | Destination |
| --- | --- |
| `data-i18n="message.key"` | `textContent` |
| `data-i18n-title="message.key"` | `title` |
| `data-i18n-aria-label="message.key"` | `aria-label` |
| `data-i18n-placeholder="message.key"` | `placeholder` |
| `data-i18n-content="message.key"` | `content`, for example on a metadata element |

Bindings support the built-in `{version}` parameter from `APP_VERSION`.
Use parameterless keys for other static labels. Messages with other dynamic
values must be rendered explicitly with `msg` or `htmlMsg`; there is no
`data-i18n-params` attribute.

For a label containing both translated text and a user value, use separate
elements or render one complete keyed message with named parameters. Avoid
binding `data-i18n` to a container with controls or other child markup, because
assigning `textContent` replaces its children.

## Plural messages

Use `msgCount` when a count changes the wording. Define the applicable cardinal
plural categories as suffixes on the same base key. Danish, English and German
use `.one` and `.other`:

```js
// Example German catalog entries:
"example.items.one": "{count} Eintrag auf {server}",
"example.items.other": "{count} Einträge auf {server}",

// Plain-text rendering:
msgCount("example.items", itemCount, { server: server.label });
```

`Intl.PluralRules` chooses the category for the selected locale, and `fmtNum`
formats `{count}`. Do not select the singular form with `count === 1`:
fractional counts can follow different rules across languages. Escape the
returned message with `escapeHtml` if it is inserted into an HTML template.

## Adding another language

1. Add its supported code, native label and locale to `SUPPORTED_LANGUAGES`.
   The language selector is generated from this registry.
2. Add a complete catalog to `I18N` with the same semantic keys and named
   placeholders as English. Include any additional cardinal plural categories
   required by its `Intl.PluralRules` locale, and update the parity checks to
   distinguish those categories from ordinary message keys.
3. Translate labels, help text, empty states, validation and action messages,
   confirmations, accessibility text and chart labels. Preserve technical names
   and user/API values.
4. Allow the new code as a configured `defaultLanguage`: extend
   `validateRuntimeConfig` in `index.html`, `LANGUAGES` and its validation error
   message in `tools/render_config.py`, and the enum in
   `config/config.schema.json`. Update the configuration tests to cover the new
   default so the browser, renderer and schema accept the same languages.
5. Add a corresponding README and commented nginx example, and update language
   navigation links and the language list in the existing documentation.
6. Update the expected language metadata and selector entries in the tests, then
   run the checks below and the renderer tests
   (`python3 -m unittest discover -s tests -p 'test_render_config.py'`). Review
   the interface in the new language for layout, wording and formatting.

## Verification

Run the dependency-free unit suite from the repository root with Node.js 24:

```bash
node --test tests/i18n.test.cjs
```

The suite reads the production script directly from `index.html`. It evaluates
declarations before the `// Start the dashboard.` marker in an isolated VM,
with browser storage and explicit DOM bindings stubbed. It does not connect to
Pi-hole instances or invoke the dashboard bootstrap.

Checks cover catalog and parameter parity, statically referenced keys including
conditional branches and tab definitions, preference resolution, English
fallback, raw-value preservation, HTML escaping, plural categories, number and
date formatting, explicit DOM bindings, storage restrictions and language
selector persistence. They also reject the former replacement-based
translation code and mutation observers.

Browser-level verification complements these checks by exercising actual
navigation, forms, charts and asynchronous API responses in each language.
Playwright is a development-only dependency pinned by `package.json` and
`package-lock.json`; it is not needed to deploy or run the dashboard.

Install the test dependencies and Chromium, then run both suites:

```bash
npm ci
npx playwright install chromium
npm test
```

The suites can also run separately:

```bash
npm run test:unit
npm run test:browser
```

If a compatible Chromium executable is already installed, the browser suite
can use it explicitly:

```bash
PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH=/path/to/chrome node --test tests/browser.test.cjs
```

By default, chart tests use a deterministic Chart.js fixture to inspect labels,
formatting and lifecycle without downloading a library. To run the same tests
with the actual separately installed Chart.js 4.4.1 bundle, set
`CHART_JS_PATH=/path/to/chart.umd.min.js` as well.

The browser tests use controlled API fixtures. They do not require access to
real Pi-hole instances. The `i18n` GitHub Actions workflow runs the automated
checks on pushes and pull requests.
